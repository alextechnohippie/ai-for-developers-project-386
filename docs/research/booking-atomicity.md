# R1 — Атомарность бронирования при конкурентных запросах (in-memory, Ktor/Kotlin)

## Вопрос

Как гарантировать, что при одновременных запросах на бронирование одно и то же время
не будет занято дважды, если хранилище — простая in-memory структура в приложении на
Ktor (Kotlin), а запросы обрабатываются в корутинах? Это фактологический сбор для
будущего решения в T2 («Модель занятости и разрешение конфликтов», issue #4) —
проектных решений здесь не принимается.

Контекст стека: Kotlin 2.2.20 + Ktor 3.6.1 (JDK 21), пакет `calendar`, in-memory
хранилище, сбрасывается при рестарте.

## Важный факт о модели потоков Ktor

Ktor обрабатывает входящие запросы на корутинах, которые выполняются не на одном
потоке, а на пуле воркер-потоков движка. В документации движков Ktor описаны
параметры конфигурации пулов — `connectionGroupSize`, `workerGroupSize` и
`callGroupSize` (последний — это пул, на котором выполняется код приложения,
т.е. корутины обработчиков), настраиваемые в `embeddedServer { configure { ... } }`
или через `ktor.deployment`. [Ktor Docs — Engines](https://ktor.io/docs/server-engines.html)

**Следствие:** два одновременных HTTP-запроса на бронирование почти наверняка
выполняются на *разных* потоках пула параллельно (а не кооперативно по очереди на
одном потоке, как в однопоточных event-loop моделях). Значит, критическая секция
«проверить слот свободен → записать бронь» подвержена настоящей гонке потоков, а не
только гонке корутин на одном потоке — наивная проверка `if (free) put(...)` без
синхронизации не является безопасной.

## Подходы

### 1. `synchronized` / `@Synchronized` (JVM-монитор)

**Суть.** Java/Kotlin `synchronized` блок или аннотация `@Synchronized` оборачивает
метод/блок монитором инстанса (или класса для статических членов) — классический
mutual exclusion на уровне JVM-потоков. [Kotlin stdlib docs —
`@Synchronized`](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.jvm/-synchronized/)

- Аннотация `@Synchronized` эквивалентна ключевому слову `synchronized` в Java-методе.
- Применяется к функциям и геттерам/сеттерам свойств; для extension-функций
  **не рекомендуется** (монитор берётся от класса-фасада, а не от логического
  владельца), в этом случае рекомендуется использовать функцию `synchronized(lock) { ... }`
  с явно указанным объектом-локом.
- Начиная с Kotlin 1.8 аннотация **deprecated** (с версии 2.1 — ошибка компиляции) для
  немультиплатформенного кода, так как синхронизация на инстансе класса не
  поддерживается на платформах кроме JVM. Для мультиплатформенного кода предлагается
  своя optional-expectation аннотация с typealias на `kotlin.jvm.Synchronized`.

**Плюсы.** Просто, хорошо изучено, работает как классический JVM-монитор.

**Минусы для Ktor-корутин.** `synchronized` — это **блокирующая** примитив: поток,
вошедший в блок, физически останавливается до освобождения монитора. Внутри
`suspend`-функции это означает блокировку потока из пула диспетчера (например,
`Dispatchers.IO`/`Default`), на котором могут выполняться и другие корутины —
блокировка одного потока снижает параллелизм пула и может привести к его истощению
при высокой нагрузке. Кроме того, `synchronized` не является suspend-aware: внутри
такого блока нельзя безопасно вызывать другие `suspend`-функции (можно случайно
приостановить корутину, удерживая монитор, что не то же самое, что освобождение
лока, и ведёт к трудно диагностируемым багам). Аннотация `@Synchronized` к тому же
deprecated/error для немультиплатформенного Kotlin.

**Пригодность.** Применим только если критическая секция синхронная и очень короткая
(без `suspend`-вызовов внутри), и если приемлемо кратковременно блокировать поток
пула. Для Ktor-хендлеров это рискованная идиома — лучше избегать.

### 2. `kotlinx.coroutines.sync.Mutex` + `withLock`

**Суть.** `Mutex` — примитив взаимного исключения для корутин: два состояния
(*locked*/*unlocked*), `lock()`/`unlock()`/`tryLock()`, свойство `isLocked`.
Ключевое отличие от `synchronized`: **`Mutex.lock()` — suspend-функция, она не
блокирует поток**, а приостанавливает корутину, позволяя потоку обслуживать другие
корутины. По memory-семантике аналогичен `synchronized`-блоку на JVM: операция
`unlock` находится в happens-before отношении с каждым последующим успешным `lock`
на этом же мьютексе. Мьютекс **не реентрантен** — повторный `lock()` из той же
корутины/потока, которая уже держит лок, всё равно приостановит вызывающего.
Рекомендуемый способ использования — extension-функция `withLock { ... }`, которая
инкапсулирует паттерн `lock(); try { action() } finally { unlock() }`.
[kotlinlang.org — Shared mutable state and concurrency](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html);
[kotlinx.coroutines API — `Mutex`](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.sync/-mutex/)

Из официального руководства по shared mutable state: обычный `synchronized`/
`ReentrantLock` — это блокирующее решение «в блокирующем мире»; «корутинная
альтернатива называется Mutex» (перефразируя оригинал: "Coroutine's alternative is
called Mutex").

**Плюсы.** Не блокирует поток-носитель — поток свободен обслуживать другие корутины
во время ожидания лока; внутри `withLock { }` можно безопасно вызывать другие
`suspend`-функции; официально рекомендуемая, suspend-aware идиома именно для
корутинного кода; гарантии видимости (happens-before) сопоставимы с `synchronized`.

**Минусы.** Чуть больше оверхед/код по сравнению с атомарными операциями на
конкурентной коллекции; не реентрантен (повторный вход из той же корутины
приведёт к deadlock, если не использовать `owner`-токен для диагностики); нужно
явно создавать и хранить один `Mutex` как синглтон на ресурс (например, на
хранилище бронирований), а не создавать новый на каждый запрос.

**Пригодность.** Хорошо подходит, если критическая секция должна включать
`suspend`-вызовы (например, обращение к внешнему сервису/БД в будущем) или если
естественнее выразить логику в виде `suspend`-блока. Для чисто in-memory структуры
без `suspend`-вызовов внутри секции — рабочий, но не самый дешёвый вариант по
сравнению с подходом №3.

### 3. Конкурентные коллекции: `ConcurrentHashMap` + атомарные `putIfAbsent`/`compute`/`computeIfAbsent`

**Суть.** `java.util.concurrent.ConcurrentHashMap` — хеш-таблица с полной
конкурентностью чтений и высокой ожидаемой конкурентностью обновлений; все операции
потокобезопасны, но операции чтения (`get`) не требуют блокировки и не блокируют
обновления. Обновление по ключу находится в happens-before отношении с последующим
чтением того же ключа, отражающим это обновление. [Java SE 21 API —
`ConcurrentHashMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)

Для атомарной идиомы «проверить-и-вставить» ключевые методы:

- **`putIfAbsent(key, value)`** — «если ключ ещё не ассоциирован со значением,
  ассоциирует его с данным значением. Это эквивалентно `if (!map.containsKey(key))
  return map.put(key, value); else return map.get(key);`, **за исключением того, что
  действие выполняется атомарно**» (точная формулировка Javadoc).
- **`computeIfAbsent(key, mappingFunction)`** — «если ключ ещё не ассоциирован со
  значением, пытается вычислить его значение через переданную функцию и внести в
  карту, если результат не `null`. **Весь вызов метода выполняется атомарно.**
  Переданная функция вызывается ровно один раз на вызов метода, если ключ
  отсутствует, иначе не вызывается вовсе... Некоторые попытки обновления картой
  другими потоками могут быть заблокированы на время вычисления, поэтому вычисление
  должно быть коротким и простым» (точная формулировка Javadoc).
- **`compute(key, remappingFunction)`** — аналогично, «весь вызов метода выполняется
  атомарно», ровно один вызов функции на вызов метода.

Эти три метода — именно та примитивная «check-and-insert» идиома, которая нужна для
«проверить, что слот свободен → записать бронь» без отдельного внешнего лока.

**Плюсы.** Нет блокировки потока в духе `synchronized` для операций чтения; атомарность
check-and-insert гарантирована самой JVM/библиотекой без ручного управления локами;
минимальный код (`bookings.putIfAbsent(slotKey, booking) == null` → слот был
свободен и теперь занят; ненулевой возврат → слот уже был занят, бронирование
отклоняется); естественно потокобезопасно независимо от того, сколько потоков из
пула Ktor конкурируют за один и тот же слот.

**Минусы.** Подходит только для простых операций типа «одна запись = один ключ».
Если правило «свободен/занят» сложнее одного ключа (например, нужно проверить
диапазон перекрывающихся интервалов — слот «Консультация» 30 минут может
перекрываться с уже существующей «Знакомство» 15 минут, начинающейся на 10 минут
позже), атомарность одного `putIfAbsent`/`compute` по одному ключу недостаточна:
нужно либо нормализовать модель занятости до дискретных слотов фиксированного шага
(тогда один слот = один ключ, и `putIfAbsent` работает идеально), либо защищать более
widкую проверку диапазона внешним `Mutex`/блокировкой. Функция внутри `compute`/
`computeIfAbsent` не должна быть `suspend` и не должна сама модифицировать карту
(это явно запрещено Javadoc) — то есть весь бизнес-код проверки должен быть
синхронным и быстрым.

**Пригодность.** Отлично подходит для Ktor-корутин: не блокирует поток, не требует
`suspend`, тривиально безопасен при параллельных запросах на пуле воркеров. Требует,
чтобы модель данных была сведена к «один слот — один ключ карты».

## Рекомендация

Для текущего кейса (in-memory хранилище, шаг «Каркас», два типа встреч с
фиксированной длительностью) **приоритетный подход — `ConcurrentHashMap` с
атомарным `putIfAbsent` (или `compute`/`computeIfAbsent`)** по ключу слота:

- Критическая секция «проверить свободен → записать» — синхронная, без `suspend`
  внутри, а значит атомарные методы карты полностью покрывают задачу без блокировки
  потоков пула Ktor.
- Это снимает риски, присущие `synchronized`/`@Synchronized` (блокировка потока
  диспетчера, deprecated-статус аннотации, несовместимость с suspend-вызовами внутри
  секции).
- `kotlinx.coroutines.sync.Mutex.withLock` стоит держать в резерве как запасной
  вариант **только если** будущая реализация T2 потребует `suspend`-вызовов внутри
  критической секции (например, обращение к внешнему хранилищу/БД вместо чистой
  in-memory структуры) — тогда `Mutex` корректно приостанавливает корутину без
  блокировки потока, в отличие от `synchronized`.
- Если модель занятости в T2 окажется не сведённой к «один слот — один ключ» (учёт
  перекрывающихся интервалов разной длительности), атомарности одного вызова карты
  может не хватить — в этом случае понадобится либо дискретизация временной шкалы на
  минимальный шаг (например, 5 или 15 минут) под единый ключ, либо оборачивание
  более широкой проверки диапазона в `Mutex`/единую точку сериализации записи.
- `synchronized`/`@Synchronized` не рекомендуется как основной механизм: блокирует
  поток пула Ktor, не suspend-aware, а аннотация deprecated (error с Kotlin 2.1).
